# ДЗ 1. Рекомендательные теги в поиске

Версия работы в формате Word лежит в этом же репозитории.

## 1. A/B-тест

### Данные из задания

- DAU: 5 000 000
- 4 поиска на пользователя в день
- теги показываются в 60% поисков
- CTR сейчас 3%, хотим увидеть 3,3% (это +10%)
- alpha = 0,05, мощность = 0,8
- единица рандомизации пользователь, тест не больше 14 дней

### Допущения

1. Подходящих запросов 30% от поисков с тегов. Это допущение, оно проверяется в части 2. Новые теги видят только эти запросы, поэтому выборка считается по ним, иначе эффект +10% разбавится.
2. Базовый CTR на подходящих запросах 3%.
3. Поиски одного человека похожи друг на друга: корреляция rho = 0,05 (по истории уточняется).
4. Тест идёт 14 дней: два полных недельных цикла, меньше влияет эффект новизны.

### Сколько нужно поисков

Формула для сравнения двух долей:

```
n = (z(1-alpha/2) + z(1-beta))^2 * [p1(1-p1) + p2(1-p2)] / (p2 - p1)^2
```

Значения: z(0,975) = 1,96, z(0,8) = 0,84, p1 = 0,03, p2 = 0,033.

```
n = 2,8^2 * (0,0291 + 0,0319) / 0,003^2 ~ 53200
```

Получается около 53 200 подходящих поисков на каждую группу.

### Поправка на пользователей

Делятся на группы пользователи, а не поиски, поэтому нужен design effect:

```
DEFF = 1 + (m - 1) * rho
```

m это число подходящих поисков одного пользователя за тест:

```
m = 4 * 0,6 * 0,3 * 14 ~ 10
DEFF = 1 + 9 * 0,05 = 1,45
пользователей на группу = 53200 * 1,45 / 10 ~ 7700
```

Чувствительность к допущениям (пользователей на группу):

- rho = 0,02: около 6 200, rho = 0,10: около 10 100
- доля подходящих запросов 20%: около 10 200, 50%: около 5 700

### Итоговый выбор

Трафика нужно трогать как можно меньше, а тест может идти до 14 дней, поэтому берём максимальную длительность. С запасом на неточность rho и s закладываем 10 000 пользователей на группу.

Контроль теста: A/A-тест до запуска, проверка баланса групп (SRM), фиксированный горизонт без подглядывания. Guardrail-метрики: конверсия поиска в заказ, доля поисков без клика, доля пустых выдач, латентность.

## 2. Правила отбора запросов

Запрос получает рекомендательные теги, если он широкий (фильтры по типу товара не помогают) и модель умеет по нему предлагать теги. Все метрики считаются по логам за 30 дней. Пороги стартовые, потом подбираются по процентилям.

1. Доля самого частого типа товара в топ-50 выдачи меньше 50%, и есть не меньше 3 типов с долей от 10%.
2. Доля сессий, где после запроса идёт переформулировка, не меньше 25%.
3. CTR текущих тегов-фильтров на запросе ниже медианы по всем запросам.
4. У запроса не меньше 100 поисков за 30 дней, чтобы оценки были стабильными.
5. Суммарная вероятность трёх лучших тегов модели не меньше 0,3.

Исключения: брендовые, навигационные и модельные запросы («iphone 15», артикулы), для них фильтры по атрибутам работают хорошо.

Правило 1 главное, остальные его уточняют.

## 3. Проверка до запуска теста

1. Ручная разметка 300 случайных запросов («широкий» или «узкий») двумя асессорами. Согласованность kappa не меньше 0,6. Precision правил не меньше 0,8, recall не меньше 0,6.
2. Офлайн-проверка модели: hit-rate@3 на отобранных запросах должен быть заметно выше, чем на отброшенных.
3. Оценка охвата: доля отобранных запросов в трафике и есть s из части 1. Если она сильно отличается от 30%, выборку пересчитываем.
4. Стабильность: пересечение набора запросов между соседними месяцами не меньше 80%.
5. Пороги и правила фиксируем до старта и во время теста не меняем.

## 4. Итоги

- Нужно около 53 200 подходящих поисков на группу, с поправкой на пользователей около 7 700.
- Тест: 10 000 пользователей на группу, 20 000 всего (около 0,4% DAU), 14 дней.
- Правила: широкая выдача, много переформулировок, низкий CTR текущих тегов, объём от 100 поисков, уверенность модели от 0,3.
