# Дизайн A/B-теста рекомендательных тегов

## Часть 1. Дизайн теста

**Формула** (сравнение двух долей, двусторонний тест):

$$n = \frac{(z_{1-\alpha/2} + z_{1-\beta})^2 \cdot [p_1(1-p_1) + p_2(1-p_2)]}{\Delta^2}$$

- $z_{1-\alpha/2} = 1{,}96$; $z_{1-\beta} = 0{,}84$; сумма 2,80; квадрат ≈ 7,85
- $p_1 = 0{,}030$; $p_2 = 0{,}033$; $\Delta = 0{,}003$
- $p_1(1-p_1) + p_2(1-p_2) = 0{,}0291 + 0{,}0319 = 0{,}0610$

$n = 7{,}85 \cdot 0{,}0610 / 0{,}000009 \approx$ **53 200 поисков с тегами на группу**.

### Допущения

1. **Доля подходящих запросов s = 30 %** от поисков с тегами (результат Части 2, проверяется на логах). Анализ ведём только по этим запросам: на остальных тест ничего не меняет, и эффект +10 % разбавился бы. Базовый CTR на подмножестве принимаем равным 3 %.
2. **Рандомизация по пользователю, анализ по поискам.** Поиски одного пользователя коррелируют, поэтому вводим design effect: DEFF = 1 + (m − 1)·ρ, где m — число подходящих поисков на пользователя за тест, ρ = 0,05 (уточняется по истории). CTR считаем как отношение сумм, дисперсию оцениваем дельта-методом или бутстрэпом по пользователям.
3. **Длительность 14 дней:** максимум по условию, два полных недельных цикла (сезонность по дням недели) и сглаживание эффекта новизны.

### Расчёт

- Подходящих поисков на пользователя в день: 4 · 0,6 · 0,3 = 0,72. За 14 дней m ≈ 10.
- DEFF = 1 + 9 · 0,05 = 1,45.
- Пользователей на группу: 53 200 · 1,45 / 10 ≈ **7 700**.

| Сценарий | Пользователей на группу |
|---|---|
| Базовый (s = 30 %, ρ = 0,05) | ~7 700 |
| ρ = 0,02 / ρ = 0,10 | ~6 200 / ~10 100 |
| s = 20 % / s = 50 % | ~10 200 / ~5 700 |

**Итог:** с запасом на неточность ρ и s берём **10 000 пользователей на группу, 20 000 всего (~0,4 % от DAU)**, длительность **14 дней**. Так затронутый трафик минимален.

**Контроль:** A/A-тест перед запуском, проверка SRM, фиксированный горизонт без подглядывания. Guardrail-метрики: конверсия поиска в заказ, доля поисков без клика, доля пустых выдач, латентность.

## Часть 2. Правила отбора запросов

Запрос подходит, если он **широкий** (фильтры по типу товара не помогают) и **модель умеет по нему предлагать теги**. Метрики считаем по логам за 30 дней.

| № | Метрика | Порог (стартовый) |
|---|---|---|
| 1 | Доля топ-1 типа товара среди топ-50 выдачи | < 50 %, и ≥ 3 типов с долей ≥ 10 % |
| 2 | Доля сессий с переформулировкой запроса | ≥ 25 % |
| 3 | CTR текущих тегов-фильтров на запросе | ниже медианы по всем запросам |
| 4 | Число поисков запроса за 30 дней | ≥ 100 |
| 5 | Суммарная вероятность топ-3 тегов модели | ≥ 0,3 |

**Исключения:** брендовые, навигационные и модельные запросы («iphone 15», артикулы), где фильтры по атрибутам работают хорошо.

Правило 1 основное, остальные его уточняют. Пороги подбираем по процентилям так, чтобы охват составил 20–40 % поисков с тегами.

### Проверка до запуска

1. **Разметка.** 300 случайных запросов (стратификация по частоте), два асессора независимо размечают «широкий / узкий». Требуем κ ≥ 0,6. Правила должны давать precision ≥ 0,8 и recall ≥ 0,6 против согласованной разметки.
2. **Офлайн-качество модели.** Считаем hit-rate@3 (совпадение рекомендованных тегов с реально кликнутыми категориями или переформулировками). На отобранных запросах он должен быть заметно выше, чем на отброшенных.
3. **Охват.** Доля отобранных запросов в трафике и есть s для Части 1. Если она сильно отличается от 30 %, пересчитываем выборку.
4. **Стабильность.** Пересечение набора запросов между соседними месяцами ≥ 80 %.
5. **Фиксация.** Пороги и правила фиксируем до старта и во время теста не меняем.
